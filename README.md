# FortiGate Filesystem Hash Checker

> [!WARNING]
> This fork is in pre-production security hardening. It is designed to fail closed, but it is not yet a complete remote-attestation or production-integrity platform. Track remaining work in [HARDENING_PLAN.md](HARDENING_PLAN.md) and the repository Issues.

The tool collects or imports the output of `diagnose sys filesystem hash`, validates the evidence, and compares a new FortiGate filesystem snapshot with a trusted baseline.

## Security model

The hardened path applies these rules:

- Unknown SSH host keys are rejected by default.
- An otherwise unknown host may be accepted only with an explicit `SHA256:` host-key fingerprint pin supplied by the operator.
- Changed known host keys are rejected.
- Passwords are not accepted in command-line arguments or CSV files.
- SSH agent and normal key discovery are enabled. An identity file can be specified explicitly.
- If password authentication is unavoidable, `--prompt-password` uses an interactive prompt so the password is not placed in argv or CSV.
- The SSH shell requests a very wide PTY to avoid wrapping long FortiGate filesystem paths.
- Collection does not complete based on fixed sleeps. The FortiOS completion marker is mandatory.
- Overall and idle receive timeouts fail closed.
- The parser accepts only strict 64-character hexadecimal SHA-256 records.
- Duplicate paths, malformed records, filesystem read errors, missing completion markers, and reported/parsed file-count mismatches are rejected.
- Legacy JSON generated by the upstream script is rejected because it cannot prove collection completeness. Retained raw output with the FortiOS completion marker can be re-parsed.
- A no-change result is deliberately scoped to filesystem comparison. Baseline provenance and FortiOS build-compatibility gates are tracked separately and are not yet implemented.

The tool is not remote attestation. A FortiGate whose control plane is already fully compromised may be able to falsify command output.

## Requirements

- Python 3
- Paramiko for SSH collection
- Access to a FortiGate account permitted to run `diagnose sys filesystem hash`

Install the runtime dependency:

```bash
python -m pip install -r requirements.txt
```

Offline parsing/comparison does not establish an SSH session, but installing the declared dependency is recommended for a consistent environment.

## SSH trust bootstrap

Do not use automatic trust-on-first-use.

Before the first normal collection, obtain the FortiGate SSH host-key fingerprint through an independent trusted path. Then use one of these approaches:

1. Add the verified key to the operator's OpenSSH `known_hosts` file.
2. Use an additional reviewed `known_hosts` file with `--known-hosts`.
3. For a controlled one-time or explicitly pinned workflow, supply the independently verified fingerprint with `--host-key-sha256 SHA256:...`.

A fingerprint pin is accepted only for the exact key presented during that connection and is not persisted automatically.

## Collect a validated snapshot over SSH

Using SSH agent or discovered keys:

```bash
python fortigate_fs_hash_checker.py \
  --fortigate 192.0.2.10 \
  --username hash-auditor \
  --output ./evidence
```

Using an explicit identity file and an additional known-hosts file:

```bash
python fortigate_fs_hash_checker.py \
  --fortigate 192.0.2.10 \
  --username hash-auditor \
  --identity-file ~/.ssh/fortigate_hash_auditor \
  --known-hosts ~/.ssh/fortigate_known_hosts \
  --output ./evidence
```

Using an independently verified fingerprint pin for an otherwise unknown host:

```bash
python fortigate_fs_hash_checker.py \
  --fortigate 192.0.2.10 \
  --username hash-auditor \
  --host-key-sha256 SHA256:BASE64_FINGERPRINT_HERE \
  --output ./evidence
```

If password authentication is required:

```bash
python fortigate_fs_hash_checker.py \
  --fortigate 192.0.2.10 \
  --username hash-auditor \
  --prompt-password \
  --output ./evidence
```

The password is requested interactively. There is no `--password` argument.

## Import retained raw evidence

A raw file is accepted only when it contains a complete FortiOS result, including:

```text
Filesystem hash complete. Hashed <N> files.
```

Example:

```bash
python fortigate_fs_hash_checker.py \
  --input-new ./evidence/fortigate_hash_raw.txt \
  --output ./evidence
```

The parser verifies that the reported count equals the number of accepted hash records.

## Compare with a baseline

Both inputs may be complete raw evidence or hardened schema-v2 JSON snapshots:

```bash
python fortigate_fs_hash_checker.py \
  --input-old ./evidence/baseline.raw \
  --input-new ./evidence/current.raw \
  --output ./evidence
```

The comparison reports:

- `MODIFIED`
- `ADDED`
- `REMOVED`
- `NO_FILESYSTEM_CHANGES_DETECTED`

The last status does not claim full device integrity. It states only that the validated filesystem snapshots contain no hash differences. Baseline provenance and FortiOS build compatibility remain separate open hardening gates.

## Batch CSV

The repository includes [hash_checker.csv](hash_checker.csv) as a safe schema example.

Columns:

```text
fortigate,username,ssh_port,fortigate_hostname,input_old,input_new,output,known_hosts,host_key_sha256,identity_file
```

Password columns are rejected.

For SSH rows, leave `input_new` empty and provide `fortigate` and `username`. Authentication uses SSH agent/key discovery or `identity_file`.

For offline comparison rows, `fortigate` and `username` may be empty when `input_new` is supplied.

Malformed rows are isolated and reported by row number. The final batch summary distinguishes succeeded, changed, failed, and skipped entries.

Run:

```bash
python fortigate_fs_hash_checker.py --csv hash_checker.csv
```

## Snapshot schema

Accepted hardened JSON snapshots use schema version 2:

```json
{
  "schema_version": 2,
  "metadata": {
    "hostname": "FGT-01",
    "collection_status": "complete",
    "reported_files": 3695,
    "parsed_files": 3695,
    "collected_at": "2026-09-23T18:00:00+00:00",
    "collector_version": "0.2.0-dev"
  },
  "files": {
    "/bin/example": "<64-character SHA-256>"
  }
}
```

FortiOS model/version/build metadata and cryptographic baseline provenance are planned in subsequent hardening milestones.

## Exit codes

Current CLI behavior:

| Code | Meaning |
| ---: | --- |
| 0 | Collection/validation succeeded and no filesystem changes were detected, or a validated snapshot was collected without comparison |
| 1 | Filesystem changes were detected |
| 2 | Invalid invocation or input |
| 3 | SSH/collection failure |
| 4 | Snapshot/parser validation failure |
| 10 | Unexpected internal error |

The exit-code contract will remain under explicit release governance until the first qualified release.

## Migration from the upstream JSON format

The original JSON format stored file paths and hashes without proof that FortiOS completed collection or that every reported record was parsed. This fork rejects those JSON files by default.

If the original raw CLI output was retained and includes the FortiOS completion marker, use that raw file as input so it can be strictly re-parsed into schema v2.

## Known limitations

- Baseline cryptographic provenance is not yet implemented.
- FortiOS version/build compatibility gating is not yet implemented.
- A compromised FortiGate control plane can potentially falsify locally generated command output.
- Version-specific FortiOS regression evidence is still being expanded.
- Upstream licensing is unresolved. Do not publish a derivative release or package until the licensing issue is resolved.

See [SECURITY.md](SECURITY.md) for reporting and security policy.
